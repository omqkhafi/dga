Platform Code needs a React project with Tailwind CSS v4. These steps use Next.js. Other frameworks are covered at the end.

## New project

<Steps>
<Step>

### Create a Next.js app

```bash title="Terminal"
npx create-next-app@latest my-app --ts --tailwind --app
```

</Step>
<Step>

### Initialise Platform Code

```bash title="Terminal"
npx shadcn@latest init https://dga.omqkhafi.dev/r/dga.json
```

`dga` is a `registry:base` item. It writes `components.json` with `iconLibrary: "hugeicons"`, `rtl: true`, the Base UI style and the `@dga` registry, so `npx shadcn@latest add @dga/button` works straight away. It installs `@base-ui/react`, `cn`, `class-variance-authority` and Hugeicons. It also adds every DGA token, the dark theme and the responsive modes to `globals.css`, and sets up IBM Plex Sans Arabic with `next/font`.

</Step>
<Step>

### Set the language and direction

```tsx title="app/layout.tsx"
<html lang="ar" dir="rtl">
```

Use `lang="en" dir="ltr"` for English pages. Components need no other change.

</Step>
</Steps>

## Existing shadcn project

If the project already has a `components.json`, add the style directly:

```bash title="Terminal"
npx shadcn@latest add https://dga.omqkhafi.dev/r/dga-style.json
```

The CLI merges DGA's values into your `globals.css`. Your existing shadcn variables (`--background`, `--primary` …) now point at DGA tokens, so stock shadcn components in `components/ui` take DGA colours too. That is the only change to your theme; the DGA tokens are new variables that do not exist in a stock project. Components are a separate step and never touch `components/ui`: see [Where components are installed](#where-components-are-installed).

## Tokens only

To use the DGA tokens without any components (for example in an existing design system), add just the tokens:

```bash title="Terminal"
npx shadcn@latest add https://dga.omqkhafi.dev/r/dga-tokens.json
```

## Use the `@dga` namespace

`init …/dga.json` registers it for you. In other projects, register it once in `components.json`:

```json title="components.json"
{
  "registries": {
    "@dga": "https://dga.omqkhafi.dev/r/{name}.json"
  }
}
```

Then install items by name:

```bash title="Terminal"
npx shadcn@latest add @dga/button @dga/badge
```

## Where components are installed

Every `@dga` component is written to `components/dga/<name>.tsx`, and imported from there:

```tsx title="page.tsx"
import { Button } from "@/components/dga/button";
```

A project can already have stock shadcn, or a library derived from it, in `components/ui`. `@dga/button` and `ui/button` are different files with different APIs, so they never share a path: installing `@dga` items does not overwrite, rename or import anything in `components/ui`, and both can be used side by side. Imports between `@dga` items (Field uses Input, Search Box uses Input) point at `@/components/dga/*`, never at `components/ui`.

Two things are shared on purpose:

- `lib/utils.ts` exports `cn`, which every shadcn project already has. The `@dga` version imports `cn` from the `cn` package. The CLI asks before replacing an existing `lib/utils.ts`; either answer works, because the signature is the same.
- `lib/dga/direction.tsx` (the `direction` item, used by Tabs, Menu, Tooltip and others) lives in a `dga` folder so it cannot collide with a helper of the same name.

### Why a `target` and not an alias

The shadcn CLI writes a `registry:ui` file to the `ui` alias in `components.json` (`@/components/ui` by default). Putting `@dga` there would collide with stock shadcn, and fixing it with an alias would make every user edit `components.json`. Instead each `@dga` file declares `files[].target` (`components/dga/button.tsx`), which the CLI honours for every item type, relative to the project (and `src/` when the project has one), with no change to `components.json`. The CLI also rewrites imports between items to the aliases (`@/components/ui/input`), and keeps an import that resolves to an existing file, so a stock `components/ui/input.tsx` would have been picked up silently. The registry sources therefore import `@/components/dga/*` directly, and `bun run test:install` installs `@dga` items into a project that already has stock `button`, `input` and `dialog`, and checks that those files are byte-identical and that the project builds.

## Dark mode

Dark tokens apply under either `.dark` (next-themes, shadcn) or `[data-theme="dark"]` (the DGA site convention). Both work on `<html>` or on any element, so a single section can be dark.

```tsx title="page.tsx"
<section data-theme="dark">…</section>
```

## Other frameworks

For Vite, React Router or TanStack Start, run the same `init` command. Outside Next.js the CLI installs the font from `@fontsource/ibm-plex-sans-arabic` instead of `next/font`.

## What gets installed

| Item | Type | Contents |
| --- | --- | --- |
| [`dga`](/r/dga.json) | `registry:base` | `components.json` settings (Hugeicons, RTL, Base UI style, `@dga` registry); pulls in `dga-style` |
| [`dga-style`](/r/dga-style.json) | `registry:style` | Dependencies, CSS imports and the `cn-*` component style map; pulls in `dga-tokens`, `utils` and the font |
| [`dga-tokens`](/r/dga-tokens.json) | `registry:theme` | Every token, light and dark themes, responsive modes, Tailwind theme, shadcn mapping, base layer |
| [`utils`](/r/utils.json) | `registry:lib` | `lib/utils.ts`, which re-exports `cn` from the `cn` package (no clsx or tailwind-merge) |
| Components (`@dga/button` …) | `registry:ui` | `components/dga/<name>.tsx`; never `components/ui` |
| [`font-ibm-plex-sans-arabic`](/r/font-ibm-plex-sans-arabic.json) | `registry:font` | IBM Plex Sans Arabic 400–700, Arabic and Latin subsets |
